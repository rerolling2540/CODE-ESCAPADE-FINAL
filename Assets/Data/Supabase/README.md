# Card Data Editor

## Required ASAP database update

For the current Unity client, run **`asap_database_fixes.sql`** in the existing
project's Supabase SQL Editor. It replaces the older ten-slot-only migration as
the one-step update. Run the whole file; it preserves existing saves and card
ownership. New projects should run the base table schemas first, then this update.

This update restricts card changes to `adeventurerank60@gmail.com`, enables ten
slots, and installs `sync_player_save`. Direct client save upserts are disabled:
the RPC locks the account row, merges independent slots, preserves deletions,
and checks the last server version observed by each device before accepting a
change to a slot. Older game builds must be updated to use this RPC.

Unity refreshes short-lived access tokens in memory, retaining the rotated refresh
token. Failed initial synchronization and pending progress retry every 15 seconds
while signed in; failed inventory/history also retain their local retry queues.
Logout or restarting the game leaves account progress in its separate local cache
for the next login. No token is written to disk.

When two devices edit the same slot from different versions, the existing account
branch stays active. Unity stores the conflicting device snapshot under
`Application.persistentDataPath/CloudSaveConflicts` before replacing it and shows
a notice in the account panel. Different slots continue to merge independently.
An unreadable server response is never interpreted as an empty inventory/save.

The runtime and SQL changes must be deployed together. Until this update is run,
the game keeps pending progress locally and reports that the database needs the
ASAP migration; it does not fall back to unsafe REST upserts.

Open `Assets/Scenes/Card Data Editor.unity` and enter Play mode. The scene builds its editor UI at runtime.

## Supabase setup

1. Run `cards_schema.sql`, then `card_inventory_schema.sql`, in the Supabase SQL Editor. The second script is safe to run against the existing card table and adds the ownership tables and Unity card keys.
2. The Card Data Editor scene has the project URL and publishable key configured. Open it with the admin button in the Main Menu after signing in; it automatically reuses that game session and loads the cards. If you open the editor scene directly, return to the Main Menu and sign in first.
3. The editor uses the Supabase REST Data API on the `public.cards` table. It can list, create, update, and delete records. Each playable card needs a `game_card_key` matching its Unity `InventoryCardCatalog` ID; chest cards use `chest.<card asset name>`, and merchant-only cards use the `merchant.card.advanced.*` keys. The inventory key links an editable database catalog row to the matching Unity effect asset.
4. `image_url` is a URL reference, such as a public Supabase Storage URL. Upload the image to Storage separately and paste its public URL into the editor.

The service-role key must never be placed in the Unity client. The SQL policy allows only the admin to manage cards; the editor uses the current user's access token so row-level security remains enabled. The JWT is held in memory only and is never saved to PlayerPrefs or project files. The project URL and publishable key are safe client configuration and are saved in the scene.

## Cross-device player saves

The game supports ten save slots. Existing Supabase projects must run
`ten_save_slots_migration.sql` after the inventory and performance schemas to
allow slots 4–10 in normalized inventory and question history. It preserves
existing rows and extends the inventory RPC's accepted indexes to 0–9.
New projects can run the updated base schemas instead. Local slots work without
this migration; cloud uploads for additional slots require it.

Run `player_saves_schema.sql` in the same Supabase project's SQL Editor. The Unity login flow automatically uploads guest save slots and inventory to the signed-in user's row, or downloads the account save when the device has no local progress. If both sides have progress, it merges slot by slot and keeps the newer version of each slot with its matching inventory. Changes to save slots and inventory sync while the session is active. Row-level security restricts each user to their own save.

## Card columns

`id` is a UUID generated by Supabase. The editor reads and writes `name`, `description`, `mana`, `image_url`, `damage_type` (`0` flat, `1` percent of attacker power, `2` legacy attacker-power percent, `3` percent of target maximum health), `base_damage`, `percent_damage`, and `damage_multiplier`. The `percent_damage` value is interpreted by the selected damage type.

## Card ownership and inventory

Run `card_inventory_schema.sql` after `cards_schema.sql`. It adds the stable
`game_card_key` link to `public.cards`, seeds the existing Unity card keys,
creates `public.player_card_inventory_slots` and
`public.player_card_inventory`, and installs the authenticated RPC that replaces
one save slot's inventory atomically. The slots table records timestamps even
for an empty inventory; the card table stores one row per owned card stack with
quantity and refinement level. RLS keeps each player's rows private.

After sign-in, Unity automatically compares each local save slot's inventory
with the account's normalized inventory, keeps the newer slot, and syncs both
directions. Every local card reward, purchase, trade, or refinement then syncs
automatically. The game still keeps a local inventory copy so battles work
offline. Battle decks are built from owned copies only. Legacy saves are seeded
with the configured starter deck during the existing one-time migration.

Run `class_card_library_seed.sql` after `card_inventory_schema.sql` to add the
90 playable Warrior, Archer, and Mage library cards to `public.cards`. They are
class-restricted Syntax Merchant offers; purchase adds them to saved inventory
and the battle deck. They are not added to the five-card starter deck. If this
seed is skipped, local play still works, but Supabase inventory sync cannot
store ownership rows for those new card keys because the database foreign key
requires a matching master card row.

The `cards` table is the editable master catalog, while battle behavior and
visuals remain authored in Unity `CardData` assets. `game_card_key` connects the
two; changing an asset's effects still requires a Unity project change.

## Question bank

Run `question_bank_schema.sql` once in the Supabase SQL Editor. It creates a
public-read-only `question_bank` table and seeds 90 questions: Java, C#, and
Python, with 10 questions per language in each level band (1–5 easy, 6–15
medium, 16+ hard). Re-running the script updates its stable question IDs.

In Unity, open the Battle Scene, select its `QuestionSystem` object, and fill
the **Supabase Project Url** and **Supabase Publishable Key** fields. Use the
project URL shown on Supabase Project Overview and the `sb_publishable_...`
key from the project's API Keys page. Do not put a secret/service-role key in
Unity. On load, the game fetches published questions. Cards and Demon Door
questions select the player's language and level band. If the remote bank
cannot be reached, cards fall back to the local `QuestionDatabase`; Demon Door
falls back to its authored questions.

The answers are returned to the game client to check them, so this database is
appropriate for a learning game but is not a secure competitive quiz bank.

The Battle Scene caches the published question bank under
`Application.persistentDataPath`, keyed by Supabase project. After one
successful download, those questions remain available offline. When connected,
Unity refreshes the cache from Supabase in the background and retries after a
network failure. The bundled `QuestionDatabase` remains the fallback when a
device has not downloaded the remote bank yet.

## Question performance reports

Run `question_performance_schema.sql` once in the same Supabase project before
using cross-device reports. It adds a topic column to `question_bank`, assigns
topics to the seeded Java/C#/Python questions, and creates the private
`player_question_attempts` table. The migration is safe to re-run. The question
editor now includes a Learning topic field for new and edited questions.

Attempts are first written to `Application.persistentDataPath` on the device,
so battle, Demon Door, and Almanac practice still record results offline. When
the player signs in, guest attempts are attached to that account and pending
records sync automatically. RLS lets each signed-in user read or write only
their own history. The Almanac's Progress report shows totals, accuracy,
completion, and per-topic mastery (at least 5 of the latest 10 responses,
3 different questions, and 80% accuracy). Guest reports show only guest attempts on that device.

Adaptive question selection and the Almanac's Recommended book use the current
language and save slot. See [Adaptive Learning](Adaptive%20Learning.md) for
progression, review rules, offline content and authoring card difficulty bounds.

Player card inventory is also stored locally per save slot. Battle, inventory,
chest, and merchant features read that local copy while offline. A signed-in
session queues failed inventory uploads and retries them periodically, and
when the app regains focus; pending local inventory is sent once Supabase is
reachable again. The question bank is read-only game content, so it refreshes
from Supabase rather than uploading player-side edits.

### Current CARDS catalog

`current_cards_seed.sql` imports the 60 assets in `Assets/Data/Cards/CARDS`
(20 Warrior, 20 Archer, 20 Mage). Regenerate it from the project root with
`node Tools/export-gameplay-cards.mjs`, then run it in Supabase SQL Editor.
`current_cards_export.json` is the readable export of the same records.

The import upserts by the asset GUID in `game_card_key`, preserving row UUIDs,
existing image URLs, other catalog rows and player inventories. Filter the
`cards` table by `source_pack = CARDS` to see the active catalog. Class,
question bounds, damage settings, VFX selection and icon GUID/fileID are
included. `card_definition` preserves the full serialized Unity effect graph,
including targeting, status stacks, repeated hits and damage caps.

Icons remain bundled Unity assets; this import records their references and
does not upload images to Storage or invent public image URLs. The game uses local CARDS assets as trusted templates, with database values applied
to runtime copies after the content migration below. Stored YAML is never executed. Cloud inventory
exports resolve legacy IDs to current CARDS keys and combine owned quantities
so they match the imported rows.


### Admin card and question editing flow

Run **content_catalog_flow.sql** in the Supabase SQL Editor after the already-installed
ASAP migration and current CARDS seed. This file is safe to rerun and does not
replace saves, inventory or answer history. No live database migration is performed
by editing Unity files. For a fresh project, install the existing schemas and CARDS
seed first. Do not rerun the seed to publish editor changes: it overwrites matching
catalog values with the exported asset values.

1. Sign in as the admin and open Card Data Editor. Select a card, change its fields,
   then Save Changes. Its immutable ownership key stays the same. Existing owners
   use the updated definition after content refresh, without losing quantity or level.
2. For a new card, choose a **gameplay template** (class, targeting, hit count,
   status effects and other behavior), then choose an icon and edit the visible
   fields. Descriptions are text; they do not create or alter effect graphs.
   Damage type/base/percentage/multiplier apply to damage effects that use those
   fields. Heal amounts, shield values and status stacks remain defined by the
   selected template. Adding brand-new behavior still requires a Unity template
   and a new game build. The template determines the class, preventing accidental
   cross-class ownership changes from a free-text field.
3. Min/max question difficulty are 1 easy, 2 medium, 3 hard. Choose the shop toggle
   and positive price. New shop offers cost coins; existing offers retain their
   configured currency. Seeded CARDS become shop-enabled at migration time with
   the default price 100. Adding a definition does **not** add it to player inventory.
   Players obtain it through the shop or an authored reward. Existing chest rewards
   still use their configured card; no random catalog-wide rewards are introduced.
4. **Retire** stops new rewards and purchases; owned copies remain resolvable and
   playable. Select a retired card and choose Restore to offer it again. If retiring
   a starter card, first update its authored starter/reward references in Unity so
   new characters still receive the intended starting deck.
5. In Question Data Editor, choose language, topic, difficulty, level range, question
   type, prompt, snippet, choices, correct answer, explanation and Published. Save
   publishes changes. **Unpublish** withdraws it from future selections after sync,
   preserving its ID and past reports. To restore, select it, tick Published and Save.
   Saved question IDs cannot be changed. Current question types still use answer
   choices; changing the type does not introduce a code-execution interaction.

Public content refreshes at startup/login, after editor writes, and every 60 seconds
while running online. Card changes are deferred during Battle Scene until leaving
that battle. An already-open question keeps its existing answer data. Successful
complete downloads replace the local cache, including an empty question bank, so
withdrawn questions do not return through a fallback. Failed requests preserve the
last valid cache. Offline devices use the last downloaded version; they need an
internet connection to receive later edits. Private save/inventory sync is separate.

Manual verification: change an owned card's mana, save and return to gameplay;
check the new mana with the same quantity. Add a template-based card and verify it
appears in the shop but is absent from inventory until purchased. Retire it and
check the owned copy still plays. Unpublish a question, synchronize, then test
again offline: it should remain absent. UI and gameplay verification requires
running Unity; the automated checks use disposable PostgreSQL fixtures.
