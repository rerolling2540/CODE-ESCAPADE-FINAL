# Card Data Editor

Open `Assets/Scenes/Card Data Editor.unity` and enter Play mode. The scene builds its editor UI at runtime.

## Supabase setup

1. Run `cards_schema.sql`, then `card_inventory_schema.sql`, in the Supabase SQL Editor. The second script is safe to run against the existing card table and adds the ownership tables and Unity card keys.
2. The Card Data Editor scene has the project URL and publishable key configured. Open it with the admin button in the Main Menu after signing in; it automatically reuses that game session and loads the cards. If you open the editor scene directly, return to the Main Menu and sign in first.
3. The editor uses the Supabase REST Data API on the `public.cards` table. It can list, create, update, and delete records. Each playable card needs a `game_card_key` matching its Unity `InventoryCardCatalog` ID; chest cards use `chest.<card asset name>`, and merchant-only cards use the `merchant.card.advanced.*` keys. The inventory key links an editable database catalog row to the matching Unity effect asset.
4. `image_url` is a URL reference, such as a public Supabase Storage URL. Upload the image to Storage separately and paste its public URL into the editor.

The service-role key must never be placed in the Unity client. The SQL policy allows authenticated users to manage the table; the editor uses the current user's access token so row-level security remains enabled. The JWT is held in memory only and is never saved to PlayerPrefs or project files. The project URL and publishable key are safe client configuration and are saved in the scene.

## Cross-device player saves

Run `player_saves_schema.sql` in the same Supabase project's SQL Editor. The Unity login flow automatically uploads guest save slots and inventory to the signed-in user's row, or downloads the account save when the device has no local progress. If both sides have progress, it merges slot by slot and keeps the newer version of each slot with its matching inventory. Changes to save slots and inventory sync while the session is active. Row-level security restricts each user to their own save.

## Card columns

`id` is a UUID generated by Supabase. The editor reads and writes `name`, `description`, `mana`, `image_url`, `damage_type` (`0` flat, `1` percent of attack), `base_damage`, `percent_damage`, and `damage_multiplier`.

## Card ownership and inventory

Run `card_inventory_schema.sql` after `cards_schema.sql`. It adds the stable
`game_card_key` link to `public.cards`, seeds the existing Unity card keys,
creates `public.player_card_inventory_slots` and
`public.player_card_inventory`, and installs the authenticated RPC that replaces
one save slot's inventory atomically. The slots table records timestamps even
for an empty inventory; the card table stores one row per owned card stack with
quantity and refinement level. RLS keeps each player's rows private.

After sign-in, Unity automatically compares each local save slot's inventory
with the account's normalized inventory, keeps the newer slot, and syncs both
directions. Every local card reward, purchase, trade, or refinement then syncs
automatically. The game still keeps a local inventory copy so battles work
offline. Battle decks are built from owned copies only. Legacy saves are seeded
with the configured starter deck during the existing one-time migration.

The `cards` table is the editable master catalog, while battle behavior and
visuals remain authored in Unity `CardData` assets. `game_card_key` connects the
two; changing an asset's effects still requires a Unity project change.

## Question bank

Run `question_bank_schema.sql` once in the Supabase SQL Editor. It creates a
public-read-only `question_bank` table and seeds 90 questions: Java, C#, and
Python, with 10 questions per language in each level band (1–5 easy, 6–15
medium, 16+ hard). Re-running the script updates its stable question IDs.

In Unity, open the Battle Scene, select its `QuestionSystem` object, and fill
the **Supabase Project Url** and **Supabase Publishable Key** fields. Use the
project URL shown on Supabase Project Overview and the `sb_publishable_...`
key from the project's API Keys page. Do not put a secret/service-role key in
Unity. On load, the game fetches published questions. Cards and Demon Door
questions select the player's language and level band. If the remote bank
cannot be reached, cards fall back to the local `QuestionDatabase`; Demon Door
falls back to its authored questions.

The answers are returned to the game client to check them, so this database is
appropriate for a learning game but is not a secure competitive quiz bank.

The Battle Scene caches the published question bank under
`Application.persistentDataPath`, keyed by Supabase project. After one
successful download, those questions remain available offline. When connected,
Unity refreshes the cache from Supabase in the background and retries after a
network failure. The bundled `QuestionDatabase` remains the fallback when a
device has not downloaded the remote bank yet.

## Question performance reports

Run `question_performance_schema.sql` once in the same Supabase project before
using cross-device reports. It adds a topic column to `question_bank`, assigns
topics to the seeded Java/C#/Python questions, and creates the private
`player_question_attempts` table. The migration is safe to re-run. The question
editor now includes a Learning topic field for new and edited questions.

Attempts are first written to `Application.persistentDataPath` on the device,
so battle, Demon Door, and Almanac practice still record results offline. When
the player signs in, guest attempts are attached to that account and pending
records sync automatically. RLS lets each signed-in user read or write only
their own history. The Almanac's Progress report shows totals, accuracy,
completion, and per-topic mastery (at least 5 of the latest 10 responses and
80% accuracy). Guest reports show only guest attempts on that device.

Player card inventory is also stored locally per save slot. Battle, inventory,
chest, and merchant features read that local copy while offline. A signed-in
session queues failed inventory uploads and retries them periodically, and
when the app regains focus; pending local inventory is sent once Supabase is
reachable again. The question bank is read-only game content, so it refreshes
from Supabase rather than uploading player-side edits.
